## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches plan | The diff's changed files and hunks, read against the plan's scope (in-scope and not-in-scope lines) and its deviation notes | Every changed file and hunk falls inside the plan's stated scope or is covered by a deviation note, and every in-scope change the plan promised is present or its absence is recorded in a deviation note or the description. Fail if the diff does more than the plan (unplanned files, features, or refactors) or less (a promised change missing) with no note covering it. | required |
| Description matches diff | The description's claims about what changed, what was deferred, and what was verified, read against the diff and the test evidence | Every material claim the description makes about the change (what behavior it fixes, which files it touches, what was removed, deferred, or left unchanged) is true of the diff, and nothing significant in the diff goes unmentioned. Small differences in quoted output wording are not drift; judge what the change does, not how a pasted message reads. A description that honestly states a limitation, a deferred edge, or a deviation passes. Fail if it claims a change the diff doesn't make, or omits a change a reviewer would need to know about. | required |
| Before/after shown | The PR's test evidence, read against the plan's test plan and the reproduction's trigger | The evidence shows the reproduced trigger (or the plan's named test) failing before the change and passing after, with the commands and their output visible. Fail if success is only asserted ("tests pass", "verified locally") with no output, or the evidence doesn't exercise the reproduced behavior. | required |
| Repo checks run | The PR's test evidence, read against the checks the repo states (PR template, CONTRIBUTING, Makefile or CI targets named in the repo facts) | The PR names the specific repo checks it ran (the command or target, such as the test suite covering the changed code) and their outcome, either with output shown or as a specific stated result. A check the author could not run passes only if the PR names it and says why. Fail if no repo check is mentioned, or the only claim is generic ("tests pass", "CI is green") with no check named. | required |
| Diff is reviewable | The unified diff and the commit list | The fix is visible and nothing unrelated rides along: no debug leftovers, dead or commented-out code, formatting churn outside the changed lines, or drive-by edits. Fail if debris or unrelated hunks are present. | required |
| Template filled | The description, read against the repo-facts block's PR template sections and contributing asks | Every section the repo's PR template asks for is present with real content for this change (a section that genuinely doesn't apply may say so). Fail if a required section is missing, left as template text, or filled with boilerplate that could describe any PR. | required |
| AI disclosure | The description, read against the repo-facts block's AI-use policy and any house rule in scope. Treat every package as AI-assisted work. | If the repo's policy or a house rule explicitly requires disclosing AI use, the description contains that disclosure with any details the policy names (such as the tool and the extent of assistance). A policy that only welcomes AI or asks for understanding requires nothing visible. Fail if a required disclosure is missing or lacks a detail the policy names. | required |
| Thread direction honored | The PR, read against explicit maintainer direction in the thread highlights or the live issue thread | The PR follows any explicit maintainer direction on approach or process, or the description says why it departs. Pass if the thread gives no direction. Fail if the PR ignores or contradicts an explicit maintainer ask. | required |

## Verdict rule

Accept if every required check passes. Preferred checks never change the verdict (this rubric has none). Any required check graded `fail` or `unclear` makes the verdict reject: a claim that can't be verified from the package counts as failing. An honestly disclosed shortfall (a deferred edge, a recorded deviation, a check named as not run with a reason) is not itself a failure; grade the check by its pass condition.
